# 屋台レジ v2 セットアップ手順

お祭り屋台向けのレジ(会計・受け渡し・現金管理)です。複数のスマホ/タブレットで同じデータを共有するため、
データの保管に **Supabase**(無料プランで可)を使います。

公開URL(変わりません): **https://ds455hid-ai.github.io/kiyora-regi/**

---

## A. はじめに 1 回だけ行う設定(約15分)

### 1. Supabase のプロジェクトを作る

1. <https://supabase.com> を開き、「Start your project」からアカウントを作成してログインします(GitHub アカウントでのログインが簡単です)。
2. 「New project」を押して、次のように入力します。
   - **Name**: `kiyora-regi`(何でもOK)
   - **Database Password**: 「Generate a password」で自動生成し、**どこかに控えておく**(後で使うことは少ないですが、忘れると再発行が必要です)
   - **Region**: `Northeast Asia (Tokyo)`
   - プランは **Free** のままでOK
3. 「Create new project」を押し、画面が切り替わるまで 1〜2 分待ちます。

### 2. データベースを作る(SQL を 1 回だけ実行)

1. 左メニューの **SQL Editor** → **New query** を開きます。
2. このリポジトリの `supabase/migrations/001_init.sql` の **全文** を貼り付けます。
   (Claude に「SQLをコピーして」と頼めば、クリップボードにコピーできます。)
3. 右下の **Run** を押します。「Success. No rows returned」と出れば完了です。
   - 2 回実行するとエラーになりますが、データは壊れません(すでに作成済みのため)。

### 3. ログインまわりの設定

1. 左メニュー **Authentication** → **Sign In / Providers**(または Providers)→ **Email** を開き、
   **「Confirm email」を OFF** にして Save します。
   (ON のままだと、スタッフ登録のたびに確認メールのリンクを開く必要があります。)
2. **Authentication** → **URL Configuration** の **Site URL** に
   `https://ds455hid-ai.github.io/kiyora-regi/` を入れて Save します。

### 4. 接続情報(2 つ)を Claude に伝える

**Project Settings**(左下の歯車)→ **API Keys**(または **Data API**)で、次の 2 つをコピーして Claude に送ってください。

| 項目 | 例 |
| --- | --- |
| **Project URL** | `https://xxxxxxxx.supabase.co` |
| **Publishable key**(旧名 anon key) | `sb_publishable_...` または `eyJ...` で始まる長い文字列 |

> ⚠️ **`service_role` / `secret` と書かれたキーは絶対に送らない・使わないでください。**
> 上の 2 つは「公開されても安全」な設計の値です(データは RLS という仕組みで守られます)。
> デプロイ用スクリプトは、秘密鍵が混ざっていたら自動で拒否します。

Claude が接続情報をアプリに設定し、動作確認(下の「C」)をしてから公開します。

## B. 公開(Claude が行います)

1. `npm run deploy` … 型チェック → 全テスト → ビルド → `gh-pages` ブランチへ反映
2. GitHub Pages の公開元を `gh-pages` に切り替え(URL は変わりません)
3. 公開 URL を開いて確認

**元に戻したいとき(ロールバック)**: GitHub の Settings → Pages → Branch を
`backup/legacy-v1`(旧レジそのもの)に切り替えるだけで、1〜2 分で旧レジに戻せます。
新レジ側の前の状態は `deploy-backup-日時` というタグにも保存されます。

旧レジは、新レジの中にも `https://ds455hid-ai.github.io/kiyora-regi/legacy/index.html` として残っています。
旧レジでためた取引履歴(各端末のブラウザ内データ)は **削除していません**。
新レジの「管理 → その他 → 旧レジ(v1)のデータ」からファイルに書き出せます。

## C. 公開前の動作チェック(任意・おすすめ)

1. アプリの「新規登録」で自分を登録します(**最初に登録した人が管理者**になります。必ずご自身が最初に登録してください)。
2. 管理者のスマホで **管理 → 営業 → 営業開始**(釣銭を金種ごとに入力)。
3. 2 台目のスマホ(またはスタッフ役の別アカウント)で新規登録し、管理者が **管理 → スタッフ → 承認する**。
4. 2 台で会計・受け渡しをして、互いの画面に即時反映されるか確認します。
5. パソコンのターミナルで自動チェックを実行すると、同時操作・権限・リアルタイム同期を一括確認できます:
   ```bash
   cd ~/kiyora-regi && npm run verify:supabase
   ```
   管理者とスタッフ(テスト用)のメール・パスワードを聞かれます(画面には表示されません)。
6. テスト会計が残るので、本番前に Supabase の SQL Editor で `supabase/maintenance/reset_test_data.sql` を実行して消します。
   (商品とスタッフは残ります。)

## D. 当日の使い方

| 場面 | 操作 |
| --- | --- |
| 営業開始 | 管理者が **管理 → 営業 → 営業開始**(釣銭を登録)。注文番号は毎営業日 001 から。 |
| 会計 | **レジ** 画面で商品をタップ → お預かり金額(1000/2000/5000/10000 ボタン・数字入力・ぴったり)→ **会計確定**。大きく出る **注文番号** をお客様へ口頭で伝えます。 |
| 受け渡し | **受け渡し** 画面に全員の注文が即時表示。品目ごとの提供(＋/−)か **提供完了**。他の人が先に押していたら自動で最新に更新され、二重提供になりません。 |
| 売り切れ | **管理 → 商品**(スタッフは **管理** から売り切れ設定のみ可)。レジのボタンが売り切れ表示になります。 |
| 返金・取消 | 管理者が **売上 → 注文履歴 → 取消・返金**(現金残高も自動で戻ります)。 |
| 釣銭補充・売上回収 | 管理者が **現金 → 補充 / 回収**。 |
| 営業終了 | 管理者が **現金 → レジ締め**(金種別の枚数を入力 → 理論残高との過不足を確認)。 |
| 売上 CSV | 管理者が **売上 → 営業日別 → 売上CSV / 現金CSV / 全期間CSV**。 |

### 電波が悪いとき
- 画面上部に赤い帯が出ます。会計は送信されません(電波が戻ると自動で最新に更新)。
- 会計確定の直後に電波が切れた場合は「**再送**」ボタンが出ます。同じ会計は **二重登録されません**。
- アプリを閉じても、未確認の会計は端末に保存されているので、開き直すと再送できます。

### スタッフの追加
スタッフが自分のスマホで **新規登録**(スタッフ名を入力)→ 管理者が **管理 → スタッフ → 承認する**。
全員の登録が終わったら、Supabase の **Authentication → Sign In / Providers** で
**「Allow new users to sign up」を OFF** にすると、知らない人が登録できなくなって安心です。

### 注意
- Supabase の **Free プランは、7 日間まったく使われないとプロジェクトが一時停止** します。
  開催の 1 週間前にダッシュボードを開いて、停止していたら「Restore」を押してください。
  イベント前に一度、アプリで会計テストをしておくのも確実です。
- 現金の「理論残高」は、開始釣銭 + 現金売上 − 返金 + 補充 − 回収 で、データベースが計算します。

## E. 仕組み(開発者向けメモ)

- フロント: Vite + React + TypeScript(静的ビルド、`base=/kiyora-regi/`、ハッシュルーティング、PWA)
- バックエンド: Supabase(Auth / PostgreSQL / RLS / Realtime)
- 会計確定・連番・提供・返金・現金は **すべてデータベースの RPC(security definer 関数)** で実行。
  テーブルは端末から読み取り専用。行ロック(営業日 → 注文 → 明細の順)・一意制約・冪等キー(`request_id`)で整合性を保証。
- テスト: `npm test`(PostgreSQL ロジック 31 件 + 本物の PostgreSQL での同時実行 8 件 + 計算ロジック 6 件)
- ローカル確認: `npm run dev:mock`(本番と同じ SQL をブラウザ内 PostgreSQL で実行する開発用モード。本番ビルドには含まれません)
